## Method

1. `cases.json` holds 34 order requests: 30 injected errors across 6 error types, plus 4 error-free controls. Each case has `source_text`, `gold` and `extractor_output`.
2. `run.py` calls `ground(extractor_output, source_text)` on each case.
3. `caught` asks for the finding code the injected error should raise, **on the item the case names** in `expect_item`: `MISSING_GTIN`, `UNGROUNDED_ID`, `REDACTED_LINK`, `UNCOVERED_LINK`, `SET_MULTIPLIED` or `VARIANT_SPLIT`. A finding with the right code on another item is not a catch.
4. `corrected` compares the returned items with `gold`. The comparison drops `uncertain` and `note`, because `ground()` sets them to explain itself and they are not extraction values. A case whose right answer is to leave the extraction alone counts as corrected when nothing changed, so `corrected` alone never proves that a check ran: read it with `caught`.
5. `false alarm` counts the 4 error-free cases where any finding appeared at all.

## Limits

- The cases are synthetic. A person wrote them to exercise the checks.
- The errors were injected by design. Real extractor errors are messier
  and often overlap: one item can lose a GTIN and invent a part number.
- The benchmark measures the checks, not an LLM. It says nothing about
  how often a real extractor makes these errors.
- `corrected` is a strict comparison. `ground()` adds a placeholder item
  for an uncovered link and never rewrites an unsupported part number,
  so those two error types cannot reach `corrected` by design.
- All 34 cases were written to fall inside the scope of the checks, so a
  high `caught` count is expected. It is not a measure of recall on real
  extractor output.
- The case set is small. One case is one data point.
